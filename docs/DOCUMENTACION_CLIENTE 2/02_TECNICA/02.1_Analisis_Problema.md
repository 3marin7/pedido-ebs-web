# Análisis del problema y contexto de uso

**Revisión:** 21 de octubre de 2026
**Estado:** hipótesis de contexto; pendiente de validar con el cliente
**Fuente:** revisión del código del proyecto y documentos preexistentes

> No se entregaron en este repositorio entrevistas, mediciones, registros operativos ni datos financieros del cliente. Por tanto, las descripciones de pérdidas, volúmenes, tiempos, porcentajes, personas y procesos manuales que aparecían en versiones anteriores no se consideran hechos observados y se retiran de este análisis.

## 1. Propósito

Este documento organiza los problemas que el sistema EBS busca atender y define qué evidencia debe recopilarse para confirmar que esos problemas corresponden a la operación real. No reemplaza un diagnóstico realizado con el cliente.

## 2. Contexto funcional inferible del producto

El código contiene funciones de facturación comercial, cobros, productos, catálogo, pedidos, inventario, clientes, reportes, cuentas por pagar y administración. Esto permite inferir que la aplicación está orientada a centralizar procesos comerciales; no permite determinar cómo opera actualmente una empresa específica ni medir el impacto alcanzado.

## 3. Hipótesis de necesidades por validar

| Hipótesis | Evidencia que debe recopilarse | Resultado a registrar |
|---|---|---|
| Puede existir duplicidad o demora en el registro de ventas | Observación del flujo actual y muestra anonimizada de registros | Volumen, frecuencia, causas y controles actuales |
| El seguimiento de cartera puede requerir centralización | Muestra aprobada de facturas/abonos y entrevistas con responsables | Proceso, estados, responsables y necesidades de alertas |
| La disponibilidad de inventario puede no coincidir con el stock real | Conteo de una muestra y comparación con el sistema existente | Diferencias, causas y frecuencia de conciliación |
| La información comercial puede estar distribuida | Inventario de herramientas, archivos y sistemas autorizados | Fuentes, duplicidad, propietario y calidad de datos |
| Se puede requerir acceso desde distintos dispositivos o con conectividad irregular | Entrevistas y pruebas en sitio | Dispositivos, conectividad y tareas offline prioritarias |

Estas hipótesis no son conclusiones ni cuantifican pérdidas.

## 4. Capacidades existentes relacionadas

En el repositorio hay interfaces y lógica para consultar/crear facturas, registrar abonos, administrar clientes y productos, manejar pedidos e inventario y presentar reportes. También existe almacenamiento local y sincronización diferida para determinados pedidos. El detalle técnico está en `02.5_Arquitectura_Tecnica.md`.

La existencia de funcionalidades en código no certifica que estén habilitadas en producción, que los datos sean correctos o que satisfagan el proceso del cliente.

## 5. Datos que faltan para un diagnóstico real

- Razón social, actividad, sedes, procesos incluidos y responsables que participaron.
- Volumen de ventas/facturas, cartera, productos y usuarios, con periodo y fuente verificables.
- Muestra anonimizada de errores, diferencias de inventario, tiempos de proceso y pérdida documental.
- Sistemas actuales, procedimientos, conectividad y dispositivos utilizados.
- Requisitos tributarios y alcance de facturación que utiliza la empresa.
- Costos actuales, metodología de cálculo y aprobación del cliente para cualquier ROI.

No incluir información personal o financiera identificable en ejemplos de documentación; usar datos anonimizados o sintéticos marcados como tales.

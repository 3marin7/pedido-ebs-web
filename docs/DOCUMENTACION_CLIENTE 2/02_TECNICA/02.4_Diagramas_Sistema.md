# Diagramas del sistema EBS

**Revisión:** 21 de octubre de 2026
**Base:** rutas, componentes y clientes de servicio visibles en el repositorio
**Alcance:** diagramas lógicos; no sustituyen el esquema real de Supabase ni la topología del despliegue

## 1. Componentes y comunicación observados

```mermaid
flowchart LR
  N[Usuario en navegador] --> APP[Aplicación React]
  APP --> ROUTER[React Router y protección de rutas]
  APP --> AUTH[Supabase Auth]
  APP --> API[Cliente Supabase JS]
  API --> DB[(Tablas y vistas del proyecto Supabase)]
  APP --> IMG[Cloudinary en flujos de carga concretos]
  APP --> W[Enlaces WhatsApp abiertos por el navegador]
  APP --> SW[Service worker: caché estática e imágenes]
  APP --> LOCAL[IndexedDB/localForage: caché de catálogo y pedidos offline]
  LOCAL -->|sincronización cuando hay conexión| API
```

La figura no implica que todos los servicios estén configurados para producción ni que las políticas de acceso estén verificadas.

## 2. Actores y áreas funcionales

```mermaid
flowchart LR
  Publico((Visitante)) --> Catalogo[Catálogo público]
  Equipo((Usuario autenticado)) --> Login[Inicio de sesión]
  Login --> Rol[Perfil y rol en user_profiles]
  Rol --> App[Funciones habilitadas en la interfaz]
  App --> Ventas[Facturas, clientes y pedidos]
  App --> Inventario[Productos, inventario y auditoría]
  App --> Cartera[Abonos y rutas de cobro]
  App --> Reportes[Reportes de ventas y cobros]
  App --> Admin[Gastos, proveedores y administración]
```

Los roles y páginas disponibles se aplican en la interfaz; la autorización en base de datos requiere validar las políticas RLS del proyecto Supabase.

## 3. Entidades y persistencia

El código consulta tablas con nombres como `user_profiles`, `clientes`, `productos`, `facturas`, `detalles_factura`, `abonos`, `pedidos`, `historial_inventario`, `preventa_pedidos`, `gastos_empresa`, `proveedores` y `facturas_proveedores`. Se usan además tablas de límites, catálogos, inmuebles, pagos y plataformas.

No se presenta un ERD con claves o cardinalidades porque el repositorio no contiene un esquema/migraciones completos y verificables. El modelo siguiente es únicamente conceptual:

```mermaid
erDiagram
  CLIENTES ||--o{ FACTURAS : "se asocia en la aplicación"
  FACTURAS ||--o{ ABONOS : "recibe"
  FACTURAS ||--o{ DETALLES_FACTURA : "contiene"
  PRODUCTOS ||--o{ DETALLES_FACTURA : "se referencia en ventas"
  CLIENTES ||--o{ PEDIDOS : "puede generar"
  PRODUCTOS ||--o{ MOVIMIENTOS_INVENTARIO : "puede registrar"
```

Las relaciones dibujadas deben confirmarse contra el esquema instalado antes de usarse para migraciones o auditorías.

## 4. Flujo conceptual de pedido offline

```mermaid
sequenceDiagram
  actor Usuario
  participant UI as Aplicación web
  participant Local as IndexedDB/localForage
  participant SB as Supabase
  Usuario->>UI: Registra pedido
  alt Hay conexión
    UI->>SB: Consulta/guarda datos del pedido
    SB-->>UI: Resultado
  else Sin conexión o timeout
    UI->>Local: Guarda pedido pendiente
    Note over UI,Local: La disponibilidad offline se limita a flujos implementados
    UI-->>Usuario: Confirma almacenamiento local según el flujo
  end
  UI->>SB: Reintenta sincronización al recuperar conexión
  SB-->>UI: Resultado de sincronización
```

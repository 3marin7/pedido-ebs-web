# Plan de instalación y despliegue
## Sistema EBS

**Revisión:** 21 de octubre de 2026
**Estado:** guía de preparación; el despliegue de producción no está verificado
**Proveedor, URL, cliente y responsables:** por confirmar

> El repositorio contiene el código y configuración del frontend, pero no acredita que este proyecto esté desplegado, en qué proveedor o con qué dominio. Tampoco confirma que el esquema de Supabase, roles, políticas RLS, backups o Cloudinary estén configurados. Este documento no establece precio, plazo, SLA ni garantía.

## 1. Requisitos identificados en el repositorio

- Node.js/npm compatibles con las dependencias del proyecto.
- Dependencias instaladas desde el lockfile del proyecto.
- Variables `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` para compilar y ejecutar la aplicación.
- Proyecto Supabase configurado con las tablas y permisos que utiliza la aplicación.
- Cuenta de almacenamiento de imágenes solo si se habilitan flujos que cargan archivos a Cloudinary.
- Un proveedor de hosting estático que soporte SPA y fallback de rutas, seleccionado por el responsable.

No incluir claves `service_role`, contraseñas de base de datos ni otros secretos en variables con prefijo `VITE_`; esas variables se incorporan al bundle del navegador.

## 2. Procedimiento antes de desplegar

1. Confirmar responsable/titular del hosting, dominio, Supabase y Cloudinary, si aplica.
2. Identificar el commit/tag que se liberará y conservar el build asociado.
3. Revisar esquema, datos, perfiles, roles y políticas RLS en un ambiente autorizado.
4. Configurar variables del ambiente sin incluir secretos privilegiados en el frontend.
5. Instalar dependencias con el lockfile y ejecutar:
   - `npm run lint`
   - `npm test -- --runInBand`
   - `npm run build`
6. Probar la salida compilada, el fallback del router, autenticación, rutas por rol, flujos de datos, manejo de errores, enlaces y capacidades offline parciales.
7. Revisar contenido del bundle y configuración de seguridad antes de publicar.

Los comandos anteriores son la interfaz de scripts definida por `package.json`; el resultado de estas pruebas debe registrarse para la versión entregada.

## 3. Procedimiento de publicación (proveedor por confirmar)

- Aplicar en el proveedor seleccionado una configuración compatible con aplicación SPA y sus rutas.
- Definir variables públicas necesarias para el build en el ambiente correspondiente.
- Publicar solo un artefacto identificado por versión/commit.
- Verificar URL, TLS, rutas públicas, sesión y acceso autorizado tras la publicación.
- Acordar y ensayar un procedimiento de reversión antes de cambios productivos.

La secuencia exacta depende del proveedor y no se prescribe Vercel, Netlify ni otro servicio como hecho actual.

## 5. Condiciones fuera de este plan

Migración de datos, capacitación, operación de servicios, monitoreo, copias y soporte requieren alcance, responsables, precio y criterios acordados por separado. La publicación del frontend no constituye por sí sola una entrega aceptada del servicio completo.
